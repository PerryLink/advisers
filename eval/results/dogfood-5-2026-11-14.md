## Findings during dogfood (fixed in the harness)

1. **Real bug in the runner**: candidate-id regex stopped at the first
   underscore (`/^(cand_[A-Za-z0-9]+)/`), but real ids are
   `cand_mwg1cau7_abc123`; `memory accept` then failed with "candidate not
   found". Fixed to `/^(cand_[A-Za-z0-9_]+)/`.
2. **Fixture issue**: P5-t3 text was a counterparty request ("张先生…要看到…"),
   not a user commitment; capture correctly returned no candidates. Rewritten as
   an explicit first-person promise. P1-t3 was similarly made explicit.
3. **Capture flakiness observed once**: v3 P1-t3 returned zero candidates for a
   clear commitment text, while 3/3 manual repeats of the same text returned two
   candidates (due 11-13 / 11-16). This is recorded as a reliability observation:
   a transient model/validation empty result is possible; a single retry on
   empty/invalid capture output is a candidate product improvement (not
   implemented in this round).
4. v1 (before the id fix) had P1-t3/P5-t3 accept failures; v2 (before fixture
   fixes) had P5-t3 fail; v4 is the clean run.
