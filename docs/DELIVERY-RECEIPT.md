# Delivery receipt pack and evidence pack v2 (verifier accepts v1)

> Status: format + library implementation for **Advisers 0.4.1** (2026-11-21; the
> formats are those shipped in 0.4.0 and are unchanged by the 0.4.1 follow-up patch).
> This document defines two on-disk formats — the **delivery receipt pack**
> (manifest v2) and the **evidence pack** (manifest v2 since 0.4.0) — the offline
> verifier contract, and the legal wording boundary. The delivery receipt pack
> was introduced as "v1.1" (manifest version `1`); its manifest v2 adds
> `subject`/`scope` and row-level lineage (0.3.2). The evidence pack manifest
> moves from v1 to **v2 in 0.4.0**, adding typed source rows plus
> `byKind`/`notCheckedCount`/`verificationBasis`. The offline verifier keeps
> accepting **both v1 and v2** for each format, so receipts and evidence packs
> generated by older Advisers releases stay verifiable unchanged.

Advisers ships two different bundles. Do not mix their names:

| Bundle | Chinese name | Producer | Covers | Purpose |
| --- | --- | --- | --- | --- |
| Evidence pack (manifest v2) | 证据包 | `buildEvidencePack` | `manifest.json`, `README.txt`, `SHA256SUMS` (manifest + README only); v2 adds typed source rows, `byKind`/`notCheckedCount`/`verificationBasis` (v1 packs still verify) | Show which local source (conversation turn, mail message, KB chunk/page, web/tool/manual entry) backs a commitment/fact/preference, and how each one resolved |
| Delivery receipt pack (manifest v2) | 交付回执包 | `buildReceiptPack` | All of the above plus **copies of the delivered files**, `receipt.docx`, generator environment, verify results, optional recipient/anchors, optional `subject` + mandatory `scope`, optional row-level lineage — **every file covered by SHA256SUMS** | Show what was delivered (and to which client/project/matter), with a portable tamper-evident receipt |

The evidence pack is **not** a delivery receipt: it carries references and capped
quotes only. Use the receipt pack when an artifact leaves the machine.

## On-disk layout

```text
<receipt-pack-dir>/                 0700
  manifest.json                     0600   deliveries + generator + verify + evidence
  README.txt                        0600   human-readable summary and verify steps
  receipt.docx                      0600   generated delivery receipt (DOCX)
  SHA256SUMS                        0600   sha256 of every other file (two spaces)
  deliveries/<delivery-id>/<file>   0600   byte-for-byte copies of delivered artifacts
```

- `SHA256SUMS` never lists itself; every other file must be listed exactly once.
- Paths inside the pack are always relative POSIX paths; absolute paths are never
  written to any pack file (generator command is path-redacted).
- Line format is coreutils-compatible: `<64 lowercase hex><two spaces><relative path>`.
- `buildReceiptPack({outDir})` writes the directory itself so the 0600/0700 mode
  contract cannot be lost in a caller. It stages files, re-reads them from disk,
  recomputes every hash and only then renames the directory into place. An
  existing non-empty `outDir` is refused unless `overwrite: true`, in which case
  the old directory is moved aside (`.replaced-<timestamp>`), never deleted.

## manifest.json

Schema version **2** (`advisers-delivery-receipt-pack`). All keys are sorted;
the document is written with `stableStringify` so the same inputs + clock
produce identical bytes.

v2 is an additive change over v1: `subject` (optional), `scope` (mandatory in
v2) and row-level `clientId`/`projectId`/`matterId`/`template` (all optional,
written only when recorded). Pack files, `fileCount` semantics, SHA256SUMS
coverage and the verifier contract are unchanged.

Field rules enforced by the verifier:

- `format` exact; `version` is `1` or `2` — any other version is schema drift.
  v1 packs are validated by exactly the old rules (no subject/scope required);
  the extra v2 rules below apply only when `version` is 2.
- `createdAt` an ISO-8601 UTC timestamp.
- `generator`: `nodeVersion`/`platform` non-empty strings; `advisersVersion`,
  `templateName`, `templateVersion`, `command` strings or null.
- `scope` (v2, required): `"subject"` or `"local-all"`.
- `subject` (v2, optional): `kind` is `"client"` | `"project"` | `"matter"` |
  `"none"`. For client/project/matter at least one of `id`/`name` must be a
  non-empty string; `kind: "none"` must not carry `id`/`name` at all.
- `deliveries`: non-empty; each id unique; each file path under
  `deliveries/`, safe/relative, size a non-negative integer, sha256 lowercase hex.
- Row lineage (v2, optional): `clientId`/`projectId`/`matterId` are non-empty
  strings when present; `template` is an object whose `name` and `version` are
  non-empty strings, optional `quoteNo` a non-empty string and optional
  `dataSha256` 64 lowercase hex characters. Keys are absent when not recorded,
  so a v2 pack built without lineage keeps the v1 row shape.
- `receipt.path` is exactly `receipt.docx`; size/sha256 must agree with SHA256SUMS.
- `verify` is an array; every entry has a boolean `ok`; `verifyStatus` is
  `passed` | `failed` | `not-recorded` and must agree with the array.
- `anchors`: optional external timestamp proofs; `fileSha256` must equal the
  SHA256SUMS digest of the referenced pack file.
- `evidence`: the embedded evidence pack is validated as its own document (see
  "Evidence pack v2" below). Each quote is at most 500 characters,
  `quoteSha256` is recomputed by the verifier, and
  `entryCount`/`counts`/`sourceCount`/`missingCount` must agree with the entries;
  a v2 evidence pack additionally has its
  `byKind`/`notCheckedCount`/`unverifiableCount`/`operatorEnteredCount`
  re-checked against the entries. Full turn/mail bodies are never embedded.
- `fileCount` must equal `SHA256SUMS` entries and the number of files the
  manifest lists (delivery files + manifest + README + receipt).

## Evidence pack v2 (0.4.0)

The evidence pack is a **separate bundle** from the delivery receipt pack, and its
manifest version moves independently: the receipt manifest is v2 since 0.3.2, while
the evidence manifest is **v2 since 0.4.0**. A receipt pack embeds one evidence pack
(the `evidence` object), and `deliveries --pack` writes the evidence pack alone;
`evidence verify <dir>` validates whichever document the directory contains.

What v2 adds (all additive; v1 packs keep verifying):

- **Typed source rows.** A `sources` row carries `kind` (taxonomy below),
  `type` (where the evidence came from: `conversation`, `mail`, `kb_chunk`,
  `kb_page`, `web`, `tool`, `calendar`, `transcript`, `document`, `ledger`,
  `manual`), `resolution: "verified"` and `quoteVerified`; `unverifiable`/
  `notChecked` rows carry `kind`+`type`+`resolution`+`reason`; a `missing` row
  carries its `reason` plus an optional `kind` (only when not the default
  `observed`) and any local identifiers it has. Every row can carry typed
  identifiers such as `sessionId`/`turnId`, `messageId`/`subject`,
  `docId`/`chunkIndex`/`pageId`, `url`, `tool`, `ref` and `sourceDigest`.
  A mail or KB reference is therefore no longer reported as
  `missing(invalid_evidence)` when the underlying row exists.
- **Four honest resolution states.** `verified` (resolved against the local ledger when
  the pack was built and the quote matched), `missing` (should have resolved but the
  turn/row is gone, the session mismatched, the quote mismatched or the ref is
  unparseable), `unverifiable` (cannot be locally verified by design: operator-entered,
  mail body purged/never retained, web page never cached, tool result never stored) and
  `not_checked` (no local lookup capability was supplied for that run). A pack never
  marks manual evidence as `verified`; the verifier rejects that.
- **Evidence taxonomy `kind`** — `observed`, `derived`, `inferred`, `manual` — with
  `byKind` counting every item across all four buckets (an unknown kind is counted as
  `observed` by the builder and rejected by the verifier when declared in `byKind`).
- **Summary fields.** `byKind`, `notCheckedCount` and `verificationBasis` next to the
  existing `entryCount`/`counts`/`sourceCount`/`missingCount`; the embedded receipt
  summary also carries `unverifiableCount` and `operatorEnteredCount`.
- **`verificationBasis` semantics.** The only honest values are `build-time` (the
  default: sources were resolved locally when the pack was built) and
  `offline-consistency-only`. Offline verification of a pack proves **internal
  consistency and that the pack was not modified after generation**; it cannot replay a
  conversation turn, re-check a web page or tool result, or prove authorship or recipient
  receipt. `build-time` is a basis label, **not** a claim that someone independently
  "verified" the evidence ("已核验"/"不可伪造" must not be written).

Verifier rules for v2: declared counts must equal the recomputed tallies, `byKind` must
contain only known taxonomy kinds and sum to the item total, `verificationBasis` must be
one of the two values, and typed rows must be well formed. The verifier accepts
`version: 1` evidence packs by exactly the pre-v2 rules. `test/evidence-pack-v2.test.js` and
`test/evidence-v3.test.js` pin the v1 fixture, the four states, the counted v2 fields and
the "manual source marked verified fails" rule.

## Scope (v2): subject-scoped vs local-all

Manifest v2 records how much data the pack contains, and **both** human-readable
documents repeat the warning (Chinese + English, one line each):

| scope | Produced when | Warning in README.txt and receipt.docx |
| --- | --- | --- |
| `subject` | a `subject` with kind `client`/`project`/`matter` is given (default, or explicit) | 本包只含 <kind> <name/id> 的数据，全局 facts/preferences 默认不含。<br>This pack contains only the data of <kind> <name/id>; global facts/preferences are not included by default. |
| `local-all` | no subject, `subject:{kind:'none'}`, or explicit scope (builder default for old callers) | 本包含本机全部客户数据，勿直接发给第三方。<br>This pack contains all customer data on this machine; do not send it directly to a third party. |

- Defaults: a client/project/matter subject selects `subject`; otherwise the
  builder writes `local-all`. Contradictory explicit combinations fail closed
  (`scope:'subject'` with no subject; `scope:'local-all'` with a
  client/project/matter subject).
- `subject.kind:'none'` is an explicit "no single subject" declaration and is
  always `local-all`; it must not carry `id`/`name`.
- The fields are a **record + warning**, not a filter. Selecting which
  deliveries/evidence belong to a subject is the caller's job (the 0.3.2 CLI
  `--subject`/client wiring performs that filtering before calling
  `buildReceiptPack`). The verifier checks their shape, not completeness: a
  pack can still omit rows, and `ok:true` only means internally consistent.
- Callers that pass neither field (e.g. the 0.3.1 CLI) still get a valid v2
  pack with `scope:'local-all'` and no `subject` key, so existing CLI JSON
  keeps working but now reports `version: 2`.

## Verify offline

Preferred entry point (CLI, 0.2.0+):

```sh
advisers evidence verify ./receipt-pack
```

The CLI subcommand is offline: it reads only the given directory, never
`~/.advisers` and never the network. It prints a machine-readable JSON result
and exits 0 when `ok` is true, 1 otherwise.

Manifest **v1 and v2 are both accepted**, for both documents. A receipt pack v1 (no
`subject`/`scope`/row lineage; written by Advisers ≤0.3.1) is validated by exactly the
pre-v2 rules; an **evidence pack v1** (written by Advisers ≤0.3.2, without typed sources
or `byKind`/`notCheckedCount`/`verificationBasis`) is validated by the pre-v2 evidence
rules. 0.4.0 writes evidence v2 and 0.3.2+ writes receipt v2. `test/receipt-pack-v2.test.js`
pins a static receipt v1 fixture plus v2 positive/negative cases,
`test/evidence-pack-v2.test.js` pins the evidence v1/v2 contract, and the v2-only checks
are listed above.

Library equivalent (same code path):

```js
import { verifyReceiptPackDir } from './lib/receipt-verify.js'

const result = verifyReceiptPackDir('/path/to/receipt-pack')
// { ok, errors, warnings, dir, fileCount, checksumCount, files, checksums, manifest }
```

Coreutils fallback (also works on a clean machine with no Advisers installed):

```sh
cd receipt-pack && sha256sum -c SHA256SUMS
```

What the verifier checks: SHA256SUMS syntax/paths (rejects absolute paths,
`..`, duplicates, self-listing), every listed file present and hash-matching,
no unlisted file inside the directory, no symlinks, valid JSON + full manifest
schema, `quoteSha256` consistency, anchors cross-checked against SHA256SUMS, and
that `receipt.docx` is a real ZIP/DOCX (`word/document.xml` present).

What it cannot do: detect someone who rewrites the whole pack and recomputes
every checksum. README.txt therefore prints `anchors: NONE - this pack is not
externally anchored (local self-attestation only)` when `anchors` is empty.
The verifier also emits a warning in that case. The evidence-pack v2 count
cross-checks (`byKind`/`notCheckedCount`/...) catch a manifest edited without
recomputing a consistent tally; they do not defeat a forger who rebuilds the whole
pack, and `verificationBasis` does not change that limit.

## Building one (library)

```js
import { buildEvidencePack, buildReceiptPack } from './lib/evidence.js'

const evidence = buildEvidencePack({ store, ledger, ids, all: false })
const pack = await buildReceiptPack({
  // Rows may also carry (all optional): clientId/projectId/matterId and
  // templateName/templateVersion/quoteNo/dataSha256.
  deliveries: store.listDeliveries(10),        // rows: {id,title,tool,createdAt,validation,files}
  evidence,                                    // or evidence entry array / manifest JSON
  verifyResults: [await verifyOffice(buffer, 'docx')],
  env: { advisersVersion: VERSION, nodeVersion: process.version, templateName, templateVersion },
  subject: { kind: 'client', id: 'cl_wang', name: '王工' },  // optional (v2)
  scope: 'subject',                            // optional; default derived from subject
  recipient: { name: '王工', email: 'wang@example.com' },
  anchors: [],                                 // empty = not anchored, disclosed in README
  outDir: './receipt-pack',                    // optional; used to guarantee 0600 modes
})
```

- `deliveries[].files` accepts a path string, `{sourcePath}`, or
  `{content, name}`. Missing source files fail the build instead of being
  silently recorded.
- `subject`/`scope` (manifest v2) are optional at the API level: omit both and
  the pack is `local-all` with no subject key (the backwards-compatible path).
  `subject.kind:'none'` declares "no single subject" and forces `local-all`.
  Bad subject/scope combinations, non-string lineage ids, a template name
  without a version and a non-hex `dataSha256` all fail the build instead of
  being silently dropped.
- `summary` returns `{format, version: 2, subject: <object|null>, scope, ...}`
  next to the existing fields; `summary.version` is what the CLI prints as
  `version`.
- `receipt.docx` is generated from a spec; the optional `advisers-office` peer is
  used when installed, with a deterministic built-in DOCX writer as fallback.
  `docxBuilder` injects a custom builder; `false` forces the built-in writer.
- `SHA256SUMS` covers manifest.json, README.txt, receipt.docx and every delivery
  file. `manifest.receipt.sha256` is the receipt's own digest; a document cannot
  contain its own digest, so the receipt does not print it (it points at
  SHA256SUMS instead).
- Optional `anchors` attach an external timestamp proof to a **delivery file or
  receipt.docx** (manifest/README are generated later, so anchoring them here
  would be circular and is rejected). With `receiptDocx` injected, receipt.docx
  can be anchored too.
- `env.command` and recipient free text are path-redacted (`<path>`); evidence
  quotes are never altered (their `quoteSha256` must stay verbatim).

### Evidence pack performance cap

The old all-rows evidence pack was O(N²) (every id re-scanned `listFacts()`;
80k entries took ~114s). `buildEvidencePack` now builds one id index per pack
(linear) and caps the **default** path at `DEFAULT_MAX_EVIDENCE_ENTRIES = 2000`
entries:

- over the cap → throws `EvidencePackLimitError` (`code:
  'EVIDENCE_PACK_TOO_LARGE'`, plus `count`/`limit`/`hint`), whose message says to
  narrow with `--ids` or opt in with `--all`;
- API opt-in: `buildEvidencePack({ ..., all: true })` or `limit: Infinity`;
- CLI: map `--all` to `all: true`, keep `--ids` as the narrowing path, catch the
  error and print `error.hint` with a non-zero exit code.
- regression: `test/receipt-pack.test.js` builds an 80k-entry synthetic pack and
  asserts it stays linear and under 2 seconds.

## CLI (0.4.0)

The CLI builds and verifies receipt packs; the library is not called by hand. The
command surface and bytes are unchanged from 0.3.2 apart from additive evidence-pack v2
fields (below); 0.4.0 writes an **evidence pack v2** into the receipt and into
`deliveries --pack`, and the standalone verifier accepts v1 and v2.

0.3.2 wired the subject scope (kept in 0.4.0): `deliveries --receipt --client <id>
[--project <id>]` selects the client's/project's deliveries (current matter ownership OR
the generation-time lineage snapshot) and the evidence under those matters, records
`subject`/`scope: "subject"` in receipt manifest v2, and writes a pack that states it
contains one subject's data. Evidence global facts/preferences need
`--include-global`; `--ids` cannot be combined with a subject. Secrecy is
`max(client.secrecyDefault, matter.secrecy)` at clearance 0, and a subject client
with a protected default fails closed (`E_SECRECY_BLOCKED`).

A pack without a subject keeps the historical behavior but is a **`local-all` v2
pack** (warning: 本包含本机全部客户数据，勿直接发给第三方). The JSON `version`
field is now `2`; additive fields `scope`, `subject`, `deliveriesTotal`,
`deliveriesTruncated`, `evidenceGlobalExcluded` and
`evidenceClientDefaultExcluded` describe the new behavior.

```sh
# Build a receipt pack for recent deliveries (default: latest 100 delivery rows,
# evidence entries capped at DEFAULT_MAX_EVIDENCE_ENTRIES = 2000)
advisers deliveries --receipt [--out <dir>] [--recipient "王工 <wang@example.com>"]
advisers deliveries --receipt --client cl_123                 # subject pack (one client)
advisers deliveries --receipt --client cl_123 --project prj_1 # narrower subject pack
advisers deliveries --receipt --client cl_123 --include-global # include global facts/prefs
advisers deliveries --receipt --ids cm_...,fact_...,pref_...   # narrow the evidence (local-all)
advisers deliveries --receipt --all                            # lift the 2000 cap
advisers deliveries --receipt --force                          # replace a non-empty --out

# Verify offline: reads only <dir>, prints JSON, exits 0 (ok) / 1 (not ok).
# It needs no ~/.advisers database, no TOS acceptance record and no network.
advisers evidence verify <dir>

# The v1 evidence-only pack is unchanged (manifest/README/SHA256SUMS/DOCX receipt).
advisers deliveries --pack [--out <dir>]
```

Behaviour of `deliveries --receipt`:

- Manifest v2 scope: a subject pack records `subject` and `scope: "subject"`;
  a pack without `--client/--project` records `scope: "local-all"`, and
  README.txt / receipt.docx carry the all-customer-data warning.
- `deliveriesTotal`/`deliveriesTruncated` report the scoped delivery count
  before the readable-file and `--limit` filters (default limit 100, max 2000),
  so a bounded pack is never mistaken for the whole set.
- Default output directory: `~/.advisers/receipts/receipt-<timestamp>`; `--out`
  chooses another path. A non-empty target is refused unless `--force`, which
  moves the old directory aside (never deletes it) — see `replaced` in the
  output.
- Delivery files that no longer exist are skipped and reported on stderr; the
  receipt only covers files that are still readable. If no readable delivery
  file remains the command fails with exit 1 instead of writing a receipt that
  claims files it cannot hash.
- Evidence: every commitment/fact/preference is included through
  `buildEvidencePack`, which is capped at 2000 entries. Over the cap the command
  prints the `EvidencePackLimitError` message plus its hint (`--ids` to narrow,
  `--all` to opt in) and exits 1 without writing a pack.
- `verifyResults`: delivered DOCX/XLSX/PPTX artifacts are run through
  `verifyOffice` when `advisers-office` is available (the CLI imports the office
  `verify` submodule directly so a receipt does not pay for the xlsx/pptx
  barrel); without that optional peer the pack records
  `verifyStatus: "not-recorded"`.
- `receipt.docx` uses the office DOCX builder when present (again via the `docx`
  submodule) and the deterministic built-in writer otherwise.
- `recipient`: `--recipient "Name <mail>"`, a bare e-mail address or a bare name;
  it is an operator-entered record, not a delivery/acceptance proof.
- `anchors` are `[]` from the CLI, so README.txt states
  `anchors: NONE - this pack is not externally anchored (local self-attestation only)`.
- The command re-runs `verifyReceiptPackDir` on the finished directory and puts
  the result in the JSON output; a verification failure sets exit code 1.
- A successful pack also records a local delivery row (`tool: receipt-pack`) and
  an audit event `receipt.pack` (JSON store has no audit chain). Rows whose tool
  is `receipt-pack` are excluded when assembling a new receipt, so receipts do
  not recursively copy older receipt packs.

Output is machine-readable JSON (one object, see
[`CLI-JSON.md`](CLI-JSON.md)) with `ok`, `format`, `version` (receipt manifest `2`),
`out`, `replaced`, `deliveryCount`, `fileCount`, `verifyStatus`, `anchored`,
`recipient`, `manifestDigest`, `receiptSha256`, `evidence`, `files`,
`skippedFiles` and `verification{ok,errors,warnings,checksumCount}`. The
`evidence` block is additive: it now reports evidence `version: 2` with
`byKind`/`notCheckedCount`/`verificationBasis` (and `unverifiableCount`/
`operatorEnteredCount` in the CLI summary); no existing key was renamed or removed.

## Library entry points

  `RECEIPT_MANIFEST_VERSIONS` (= `[1, 2]`, the receipt verifier contract),

  `RECEIPT_SHA256SUMS_FILE`, `RECEIPT_FILE_MODE`/`RECEIPT_DIR_MODE`.

  (= `[1, 2]`, the evidence verifier contract), `EVIDENCE_RESOLUTIONS`
  (`verified`/`missing`/`unverifiable`/`not_checked`), `EVIDENCE_KINDS`
  (`observed`/`derived`/`inferred`/`manual`), `VERIFICATION_BASIS` (=

- exports kept: `verifyPack`, `manifestFor`, `toDocxRows`, `sha256Hex`,
  `stableStringify`, `MAX_QUOTE_CHARS`.

`packages/advisers/lib/receipt-verify.js`

- `verifyReceiptPackDir(dir)` — sync, offline directory verifier.

## Legal wording: what this pack is and is not

This is **not** an e-signature, not a CA-issued certificate, not notarization and
not a trusted timestamp. It is a local, tamper-evident, carry-anywhere receipt
whose checksums can be recomputed by anyone holding the directory.

## Privacy / scope

- Generation and verification are local and network-free; verification does not
  open `~/.advisers/state.db`.
- `scope` is a declaration + warning, not an enforcement boundary: the pack does
  not prove it contains only the declared subject's data. Do not send a
  `local-all` pack (`scope: "local-all"`, or no subject) to a third party.
- Subject ids/names and row lineage are pack metadata like the recipient field:
  they are operator-supplied and appear in plain text (subject/README/receipt);
  they are not secrets, and `subject` must not be used to smuggle contact data
  into a pack that will be shared.
- The pack copies the delivered artifacts (that is the point) but not full
  transcripts: evidence quotes are capped at 500 characters and carry
  `session#turn` references plus `quoteSha256` only.
- All paths are relative; `env.command` and recipient free text are path-redacted.
- Recipient/accept fields do not record consent, only operator input.
- Evidence `verificationBasis` is a basis label, not a verification level:
  `build-time` does not mean a human or external service reviewed the pack, and
  offline verification cannot replay turns, re-check web/tool sources or prove receipt.
- Deleting the pack does not modify the local ledger.
