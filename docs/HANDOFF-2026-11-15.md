## 1. 产品与用户意图

### 产品

**Advisers（幕僚）**：本地优先、中文、可审计的个人工作秘书 runtime。

- 目标用户：同时服务 2–5 个客户的技术型独立顾问/自由职业者/小团队负责人。
- 主形态：**CLI 是产品本体**；DSH bundle 是薄适配器（`advisers_brief` + `advisers_office`），不是第二产品。
- 三本账：
  - 用户账（facts/preferences/boundaries/evidence）
  - 承诺账（who owes whom / due / evidence / 人工 accept / receipt）
  - 流程账（routines：draft/approve/patch/diff/apply/revert）
- 一等交付物：本地 Office 文件（DOCX/XLSX/PPTX/Mermaid/draw.io/XMind），带确定性 `verify` 与 delivery receipt。
- 本地边界：SQLite 在 `~/.advisers`，默认不联网，显式 `research` 出网，secret matter fail-closed，audit hash chain。
- 明确不做：通用聊天/情感陪伴、通用 Office 编辑器、默认上传客户文件、无限深记忆、展示原始 CoT、完整 CLM/e-sign、AI 硬件/常驻录音、团队/SSO/私有化、插件市场军备、自动代发/自动改期、全功能 GUI/移动 App。

### 用户的核心要求（长期有效）

1. **中文回复**，直接、简洁、给证据；不要夸张、不要把未验证的事说成完成。
2. **能做的都要做**；用户已给广泛授权，可当作用户本人执行外部可执行动作（提交/推送/发布准备等）。
3. **工具无关交付**：Office 还是 WPS 不重要，最终格式正确、能打开、可验收即可。
4. **外部阻塞要如实记录**，不能伪造完成；不能代替真人签字/OTP。
5. 发布/版本要 bump、测试、stage、docs、commit、push 三远端。
6. 旧会话/旧索引不可作为事实源；本文件与仓库为准。
7. 当前会话将被删除；未来工作在新会话继续。

## 7. 执行经验 / 惯性 / 优点 / 缺点

### 有效的做法（继续保持）
- 先证据后结论；每条外部事实带 URL/日期；代码结论带文件/行号/命令。
- 先修“卡验收的 bug”，再补功能；E0 三 bug 就是典型。
- 每个功能都配测试 + 真实模型 smoke；发布前 build/typecheck/pack/security/docs 全跑。
- 变更走“bump → docs → commit → push 三端 → stage → 证据文件”。
- 文档必须诚实：vault 是显式 opt-in、sync 是 last-snapshot-wins、OCR 是本地适配器、office 只有 WPS 证据、没有人工金标。
- 用户给广泛授权，但外部真人/OTP 不能代做；如实说“不能”。

### 踩过的坑（新会话避免）
- npm 默认 registry 可能是 npmmirror；`stage publish` 必须显式 `--registry https://registry.npmjs.org/` 并用 token env，否则 ENEEDAUTH/EOTP。
- GitHub 全局 `url.https://gh-proxy.com/...insteadOf` 会劫持直连；推送用 `GIT_CONFIG_GLOBAL=/dev/null` + `http.proxy=` + token askpass，失败重试。
- Gitee token 用户名要用 `perrylink`；GitCode `PerryLink`；不要把 token 写进文件/输出。
- `packages/advisers` 的 `files` 曾漏 `lib/` 导致发布包缺运行文件；现在 `files: ["lib", ...]`，pack-smoke 会走 import graph（当前 35 files）。
- Node 22 会输出 `node:sqlite` ExperimentalWarning 到 stderr；解析 JSON 测试要定位真正 JSON 行，不能假设 stderr 为空（Pet Brief 的 2a4d5f4/64a7f82 就是修这个）。
- `advisers audit` 曾在 fresh home/有记录场景误报；已修，不要回退。
- continuity 曾因 agent 在回答问题时用旧消息回填 `memory_propose` 而 8/9；已加系统提示修复，复跑 9/9。
- 图像附件现在走 OCR 适配器，未配置会报 `OCR is not configured`；旧测试“unsupported attachment”已调整为兼容。
- `.70` staged 之后又来了 Pet Brief；不要假设“版本号相同=内容相同”。发布前必须重新 stage `.71`。

### 优点
- 证据链/承诺账/Office 验收/本地审计/中文承诺语义的组合，竞品没有完全对应。
- 测试面大（250），有真实模型回归，文档诚实，外部阻塞记录清楚。
- CLI 可脚本化、JSON/MCP/只读 UI 都有，适合技术型顾问。

### 缺点/风险
- **发布没完成**：staged `.70` 不含 Pet Brief，公开 next 仍是旧 0.1；版本/文档不一致。
- **质量证据仍是合成/agent review**：没有独立人工金标、真实 dogfood、真实脱敏资料；不能对外宣称“人工验证”。
- **功能深度不均**：邮件/日历只有文件/IMAP 只读，无 OAuth；同步是快照不是合并；vault/OCR 是显式适配器；Pet Brief 未接 UI。
- **staged 版本堆积很多**（`.58`–`.70` 等），清理需要 OTP；不要批量 reject 除非用户明确。
- **三远端不同步**；GitCode 落后，Gitee 未核实。
- CLI/文档复杂度高；新用户上手成本仍在。
